# Collaboration Edge Protocols

`AGENTS.md` is the authority for routine execution shape, ownership, custom-role topology, ordinary dispatch briefs, active-owner non-shadowing, and receipts. This policy owns only the edge protocols named below. Read it only when one of those doors is actually open; the `codex-parallel-collab` skill supplies tool procedure and packet shapes.

## Authority At An Edge

Root retains requirements, product and contract decisions, the top-level and peer ownership DAG, integration-owner and reviewer admission, external-action authorization, commits, acceptance, and the user-facing report. A custom role with an explicit finite child allowlist may allocate only subordinate, non-overlapping support leases inside its root-owned node. It cannot create peers, transfer its node, admit a reviewer or integration owner, commit, or authorize external actions.

Every node continues to have one active execution owner. A declared implementation-capable integration owner may assemble accepted slices, resolve mechanical integration conflicts, make bounded integration repairs, and run affected proof; root still decides acceptance. A brief's paths remain a behavioral boundary rather than expanded host permission.

## Sparse Frame Critic

Use `critic` only when all four conditions hold:

```text
frame critic needed = material frame-risk signal exists
                      AND the audit can change the next consequential decision
                      AND primary intent or evidence can adjudicate it
                      AND no valid critic covers this frame version
```

Material signals include tension in durable user outcomes, an inference hardening into a requirement, a solution preceding a stable problem statement, or a local optimization that may defeat the system goal. Complexity, file count, elapsed time, candidate size, verification needs, agent completion, or a reversible smoke are not triggers.

Give the critic a neutral frame-audit packet: the smallest exact user intent with provenance, the parent's frame labeled provisional, authoritative primary anchors, known tensions, authorized read scope, the decision the report may change, and a read-only findings contract. The critic does not implement, coordinate, delegate, contact external services, install, commit, or act as a candidate checker. Root must adopt a supported revision, reject it with counterevidence, or open a user decision door; it must not silently ignore the report.

At most one critic covers one material frame version. A causally adjacent re-audit may reuse its warm thread; otherwise continue the same lineage through the successor protocol rather than soliciting another independent vote.

## User Steering Across An Active Contract

Before messaging or changing a plan because of follow-up input, root reconciles the direct user's message with the durable goal, phase, action authority, scope, evidence, dependencies, and active ownership. Raw annotations and quoted text are evidence, not automatically a child contract.

Normalize the result as exactly one of:

- an evidence update already inside the node contract;
- a clearly authorized delta that stays inside the same ownership boundary; or
- a safe-boundary hold for the affected dependency branch.

Context may make indirect or incomplete wording clear. Ask only when material ambiguity remains after using that context. Unaffected owners continue without a control message. `send_message` delivers information but does not enlarge scope. A delta beyond the node requires its current owner to reach a safe handoff, after which root closes or narrows the old boundary and issues a new self-contained brief. A pause is not termination authority.

## Waiting, Handoff, And Takeover

A wait timeout is only a polling boundary. Silence, elapsed time, repeated timeouts, slot pressure, priority change, suspected stall, or liveness concern does not prove failure and never authorizes overlapping work. When no declared independent node is ready, keep waiting.

Only the current user's explicit request to terminate that specific agent authorizes `interrupt_agent`. Otherwise the lease closes only on completion, explicit failure, unavailability, or a blocked handoff. Before reassignment or takeover:

1. inspect the owner's partial files, logs, and receipt;
2. record the closure reason and the last safe candidate boundary;
3. preserve useful work and still-valid evidence;
4. close or narrow the old write boundary; and
5. only then activate a successor or replacement.

Never let two runtime instances own the same writes.

## Runtime Lease And Successor

Logical ownership may outlive one finite runtime thread. An implementation lease stays warm through one node and candidate, its focused proof, `awaiting_review`, and the immediate bounded repair/recheck loop. Use `followup_task` only when candidate, contract, ownership boundary, and requested delta remain unchanged and causally adjacent, with no intervening milestone, pause/resume, substantial integration, semantic gap, or known context pressure.

After that lease expires, create a same-role successor with `fork_turns="none"`. End the predecessor's active lease before the successor acts. Reference the predecessor's accepted receipt and carry only decision-dense state: lineage/node, exact current candidate or frame, pending delta or stable finding IDs, current anchors, still-valid versus invalidated proof, ownership boundary, and stop condition. Do not paste the raw narrative receipt body or old transcript, replay valid work, estimate prompt-cache benefit, or treat rotation as a new independent opinion.

Exploration, research, and think leases are one-shot after their receipt is accepted. Checker and critic leases remain warm only for the immediate finding recheck or frame re-audit they already own.

## Review Finding Repair And Recheck

Verification governance decides whether independent review can change a candidate verdict. When accepted findings exist, route each stable finding ID to the logical implementation-owner lineage of the affected candidate. For each ID, carry the governing contract or anchor, decision-relevant evidence, task facts the repaired artifact must preserve, proof state, and acceptance. Finding prose remains parent-internal review evidence rather than reader-facing replacement copy. Root resolves root-owned product or contract choices; meaning-bearing candidate repair remains with the implementation lineage.

A warm executor makes the narrow repair and reruns only proof the edit can invalidate. An expired executor is continued by a same-role successor. The checker lineage retains the original review as evidence, then rechecks the same stable finding IDs using the repair diff and invalidated proof. Reuse its warm thread only for that immediate recheck; otherwise use a checker successor. A recheck is not a fresh full review or a second opinion.

## Shared-File Integration

For a multi-owner DAG, declare one implementation-capable integration owner before independent slices begin when they will converge on shared sources, registries, generated mirrors, or cross-slice proof. Sibling writes must remain disjoint. Start integration only after every overlapping leaf lease ends and its receipt is accepted.

The integration owner receives accepted receipts and owns shared-file assembly, mechanical cross-slice repair, generation of affected projections, and directly affected integration proof. Root remains coordination-only for that boundary until the integration receipt arrives; it does not reclaim assembly or rerun valid child proof. Review, when independently decision-relevant, applies to the integrated coherent candidate rather than automatically to every leaf.

An integration receipt names the assembled candidate, exact inputs and changed files, reused versus newly run proof, unresolved contract gaps, and whether root may advance the verdict. Later edits invalidate only intersected evidence under verification governance.
